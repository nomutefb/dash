# 발행관리 설계 — 개발본과 발행본의 DB 분리 (2026-09-04)

## 1. 왜 필요한가 (문제)
- MISO 앱은 코드가 두 벌(개발 중인 미리보기 A, 발행된 B)인데 PocketBase DB 는 한 벌이다. 개발용/운영용 DB 스위치가 없다.
- 그래서 A 에서 시트 구조를 바꾸면 B 는 옛 구조로 계속 읽고 쓴다. 260903~04 청사진 작업(통합 시트) 뒤 B 가 동결된 옛 시트에 쓰는 상태가 됐었다(피해는 없었음 — 그 사이 입력 0건 실측).
- PocketBase 는 앱 폴더와 다른 컨테이너에서 돌기 때문에 "DB 를 앱 폴더 안에 두기"는 불가능(훅이 앱 폴더에 파일을 못 씀 — 260904 실측).

## 2. 해결 원리
DB 는 하나지만 **컬렉션을 둘로** 둔다.

```
요청 → 훅(ym-db.pb.js) 첫 줄: __env = envOf(e)
        ├ "dev"  → ymdata_dev / ymmeta_dev   (미리보기 화면, 개발)
        └ ""     → ymdata / ymmeta           (발행 화면, 크론, 헤더 없는 요청)
```
- 환경 판정(`api/ym-env-lib.js` `envOf`): ① 헤더 `X-Ym-Env`(앱이 자동으로 붙임) ② 없으면 Referer 에 `/service/coder/preview/` 가 있으면 dev ③ 그 외 발행본.
- dev 인데 `*_dev` 컬렉션이 없으면 **오류**로 멈춘다(발행본으로 조용히 떨어지지 않음).
- 앱(`public/standalone.html` 머리의 스크립트): 주소로 환경을 정하고 `window.fetch` 를 감싸 `__runtime/api` 요청 전부에 헤더를 붙인다. 켜진 뒤 `/api/ym/env` 의 `here` 와 비교해 다르면 붉은 띠 + 쓰기 차단.

## 3. 구성 요소
| 파일 | 역할 |
|---|---|
| `api/ym-db.pb.js` | 기존 45개 라우트. 각 핸들러 첫 줄에서 `__env`·`__col(name)` 을 만들고 모든 컬렉션 접근이 `__col` 을 거침 |
| `api/ym-env-lib.js` | `envOf`, `col`, `initDev`(스키마 복제), `refreshDev`(발행→개발 복사), 이관 실행기 |
| `api/ym-env.pb.js` | 라우트: `GET /api/ym/env`, `POST /api/ym/env/init-dev`, `POST /api/ym/env/refresh-dev`, `GET /api/ym/migrations`, `POST /api/ym/migrate` |
| `api/migrations/NNN_*.js` | 이관 스크립트. `module.exports = { id, title, up(ctx) }`. 번호순 실행, 적용 기록은 그 환경의 `ymmeta` 시트 `_ym_migrations` |
| `api/ym-ops-alias-lib.js` | `partAlias(sheet, part, app, metaCol)` — 환경에 맞는 ymmeta 를 인자로 받음 |
| `api/ym-member-summary-lib.js` | `getOrBuild(env)`/`rebuild(env)` |
| `tools/phase8*_260904.py` | 위 변경을 적용한 스크립트(앵커 assert) |

크론(`ym-crons.pb.js`, `ym-cron-lib.js`)은 요청이 없으므로 항상 발행본을 본다. 개발본에는 크론 결과(홍보 스캔·모니터)가 안 쌓인다 — 의도된 것.

## 4. 이관(migration) 규칙
- 한 파일 = 한 구조 변경. `up(ctx)` 만 있다(되돌리기는 backups/ 로).
- `ctx = { app(트랜잭션), env, col(base), sheetRows(sheet), meta(sheet), parseJson, log }`.
- 트랜잭션 안에서 실행되고, 실패하면 통째로 롤백되며 적용 기록도 남지 않는다.
- **내용 보존**: 행을 지우는 이관은 중복 제거처럼 근거가 명확한 경우만. 그 외는 열 추가/이름 변경/값 변환.
- 같은 번호를 두 환경에 각각 적용한다(dev 에서 검증 → prod 에서 실행). `force:true` 는 재실행, `only:'002'` 는 한 개만.
- 001 = 통합 시트 기준선(검증만), 002 = 일일실적 중복 정리.

## 5. 절차
**개발 시작**: `POST /api/ym/env/init-dev`(최초 1회) → `POST /api/ym/env/refresh-dev`(발행본 데이터를 개발본으로) → 미리보기에서 작업.
**발행**: CLAUDE.md §2 체크리스트. 핵심은 "이관을 prod 에 실행(내용 보존) → 코드 발행" 순서.
**개발본 초기화**: `refresh-dev` 다시(개발본은 덮어써짐. 개발본에 입력한 시험 데이터는 사라짐).

## 6. 확인 방법
- 미리보기 콘솔: `fetch('__runtime/api/ym/env').then(r=>r.json())` → `here:"dev"`, `dev.sheets`/`prod.sheets`, 이관 현황.
- 발행 화면 콘솔: 같은 호출 → `here:"prod"`.
- 격리 실측: 미리보기에서 저장 → 발행본 `/api/ops?sheet=…` 행 수 불변.

## 7. 한계 (플랫폼 구속)
- DB 하나(컬렉션 분리로 대체), 훅은 앱 폴더에 못 씀, 발행은 코드 전체 단위.
- 개발본 컬렉션은 DB 용량을 두 배로 쓴다(현재 ~2만 행 → 문제 없음).
- 이관 라우트에 인증이 없다(기존 라우트와 같은 수준). `confirmProd` 게이트만 있음.
